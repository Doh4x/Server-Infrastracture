## Установка

```bash
sudo git clone https://github.com/<вы>/server-infra.git /srv/infra
sudo bash /srv/infra/setup.sh
```

## Развернуть приложение

```bash
app deploy https://github.com/<вы>/blog.git
```

Команда склонирует репозиторий в `/srv/apps/<имя>` и задаст несколько вопросов:

- имя приложения (по умолчанию — имя репозитория);
- какой compose-файл запускать, если их несколько (`compose.prod.yaml` предлагается первым);
- значения из `.env.example`, если он есть;
- какой сервис смотрит в интернет и на каком порту он слушает внутри контейнера;
- домен.

Потом запустит приложение и подключит домен с HTTPS. В самом репозитории ничего не меняется: команда кладёт рядом `.env` и `compose.proxy.yaml`, который подключает сервис к сети `proxy` и убирает его `ports:`, чтобы наружу ничего не торчало.

Задать вопросы заново (поменять домен, порт, настройки): `app setup <имя>`.

Имя можно передать сразу (`app deploy <url> blog`), тогда команда его не спрашивает.

Приватный репозиторий: логин и пароль команда не спрашивает. Она создаст для приложения отдельный ключ только на чтение, покажет его и попросит добавить в репозиторий на GitHub: Settings → Deploy keys → Add deploy key. После этого склонирует по SSH, и `app update` дальше будет ходить с этим же ключом. Если вместо этого пишет «No access», а репозиторий публичный — проверьте ссылку.

## Команды

| Что | Команда |
|---|---|
| Развернуть из git | `app deploy <url> [имя]` |
| Список приложений, сколько контейнеров работает, домены | `app list` |
| Обновить: `git pull`, свежие образы, перезапуск | `app update <имя>` |
| Обновить все приложения | `app update --all` |
| Обновить саму инфраструктуру: `git pull` этого репозитория и `setup.sh` заново | `app self-update` |
| Логи | `app logs <имя> [сервис]` |
| Контейнеры приложения | `app status <имя>` |
| Перезапустить, остановить, запустить | `app restart <имя>`, `app stop <имя>`, `app start <имя>` |
| Удалить приложение вместе с доменами | `app remove <имя>` |
| Какие домены куда ведут | `site list` |
| Сколько памяти и процессора ест | `docker stats` |
| Логи прокси (сертификаты, ошибки 502) | `docker compose -f /srv/infra/proxy/compose.yaml logs -f` |
| Сколько места занимает Docker | `docker system df` |

`app remove` спросит, удалять ли тома с данными. По умолчанию — нет.

Ошибка 502 от прокси почти всегда значит, что приложение не запущено или при настройке указан не тот порт. Проверить: `app status <имя>`, поменять порт: `app setup <имя>`.

## Что должно быть в репозитории приложения

- `compose.yaml` или `compose.prod.yaml`;
- `.env.example` с настройками, если они нужны (пароли в git не кладутся);
- на слабом сервере лучше готовые образы (`image:`), собранные в GitHub Actions, а не сборка (`build:`) на месте.

Базы и прочие внутренние сервисы ничего особенного не требуют: в сеть `proxy` подключается только выбранный сервис, остальные видны лишь внутри приложения.

Если образ лежит в закрытом GitHub Container Registry, один раз войдите в него токеном с правом `read:packages`: `docker login ghcr.io -u <вы>`.

## Вручную, без мастера

Приложение — это папка в `/srv/apps` со своим `compose.yaml`. Сервис, который должен быть доступен снаружи, подключается к сети `proxy` под уникальным именем:

```yaml
services:
  app:
    image: ghcr.io/<вы>/blog:latest
    restart: unless-stopped
    networks:
      default:
      proxy:
        aliases:
          - blog

networks:
  proxy:
    external: true
```

```bash
docker compose up -d
site add blog.example.ru blog:3000
```

Не открывайте порты через `ports:`: Docker пробрасывает их в обход файрвола.
